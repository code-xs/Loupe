# 状态机常见缺陷模式参考

> 本文件为功能疑难专项子工作流 F2（状态机拓扑与数据流还原）提供常见状态机缺陷模式。
> State Analyst 应对照本文件检查目标代码中是否存在以下模式。

## 1. 孤岛状态 (Orphan State)

**定义**：状态机中存在某个状态，没有任何入边（无法到达）或没有任何出边（无法离开）。

**典型表现**：
- 枚举/Sealed Class 中定义了状态值，但代码中从未设置过该状态
- 某状态一旦进入就永远无法跳转到其他状态（死锁状态）
- 历史重构后遗留的废弃状态

**检测方法**：
```
遍历所有状态 S:
  入边检查: 是否存在至少一个转移 T -> S?
  出边检查: 是否存在至少一个转移 S -> T?
  若两者均不满足 → 标记为 Orphan
```

**风险等级**：Medium（无出边）/ Low（无入边，仅代码卫生问题）

## 2. 非法跳转 (Illegal Transition)

**定义**：绕过守卫条件或设计意图，直接从状态 A 跳转到不相邻的状态 C。

**典型表现**：
- 外部事件（如 DeepLink、Push 通知）直接设置状态，跳过中间流程
- 多处代码独立修改同一状态变量，缺乏统一入口
- 异常恢复路径跳过正常状态转移

**检测方法**：
```
对每一处状态赋值:
  检查赋值前的状态是否是设计允许的前置状态
  检查是否经过了守卫条件检查
```

**风险等级**：Critical（若跳转导致数据不一致）/ Major（若跳转导致 UI 异常）

## 3. 守卫缺失 (Missing Guard)

**定义**：状态转移缺少前置条件校验，导致不满足条件时也能执行转移。

**典型表现**：
- `if (currentState == A)` 但没有检查必要的数据前置条件
- 异步回调中直接执行转移，未检查当前状态是否仍然有效
- 乐观转移：先转移再验证，失败时未回滚

**检测方法**：
```
对每个状态转移 A -> B:
  列出设计上的前置条件集合
  检查代码中是否每个前置条件都有对应的 guard check
```

**风险等级**：Critical（若缺失 guard 导致数据损坏）/ Major（一般情况）

## 4. 竞态状态更新 (Race Condition on State)

**定义**：多个线程/协程同时修改状态变量，导致状态值不可预测。

**典型表现**：
- 主线程设置状态 + 网络回调线程设置状态（无同步）
- 多个 LiveData/Flow Observer 同时触发状态变更
- Actor/Channel 处理消息时未保证顺序

**检测方法**：
```
对每个状态变量:
  列出所有写入点及其所在线程
  检查是否有线程安全保护（synchronized / Mutex / 原子操作 / 主线程约束）
```

**风险等级**：Critical

## 5. 回边循环 (Back-edge Loop)

**定义**：状态转移形成循环，且缺乏有界退出条件。

**典型表现**：
- 重试逻辑：失败 → 重试 → 失败 → 重试... 无最大次数限制
- 状态机 A → B → A 循环，无稳定收敛条件
- 用户操作触发状态回退，回退后又触发前进

**检测方法**：
```
在状态图中检测环 (cycle)
对每个环检查:
  是否有计数器/超时作为退出条件
  退出条件是否可靠（不会被重置）
```

**风险等级**：Major（有界但不合理）/ Critical（无界循环）

## 6. 脏写与快照失效 (Dirty Write / Stale Snapshot)

**定义**：数据模型在传递过程中被意外修改，或消费者持有的快照已过期。

**典型表现**：
- 可变对象作为参数传递后被上游修改
- RecyclerView/UITableView 持有的数据引用被后台刷新，但未通知 Adapter
- ViewModel 缓存的数据与 Repository 最新数据不一致

**检测方法**：
```
对每个核心 Data Model:
  追踪从 Source (DB/Network) 到 Consumer (UI/Disk) 的完整路径
  检查每一层是否做了防御性拷贝
  检查是否存在 Mutable 引用泄漏
```

**风险等级**：Major（UI 不一致）/ Critical（数据损坏）

## 7. 生命周期不对称 (Lifecycle Asymmetry)

**定义**：订阅/注册操作与对应的取消/注销操作不对称，导致资源泄漏或空回调。

**典型表现**：
- onCreate 中注册监听，但 onDestroy 中未取消（Activity 重建场景泄漏）
- viewDidAppear 中订阅，viewDidDisappear 中未取消
- 协程在 CoroutineScope 外启动，Activity 销毁后继续执行

**检测方法**：
```
对每个 register/subscribe/observe 调用:
  查找匹配的 unregister/unsubscribe/removeObserver
  验证 pair 是否在对称的生命周期回调中
```

**风险等级**：Major（泄漏）/ Critical（空引用崩溃）

## 使用指南

State Analyst 应在分析过程中：
1. 逐一对照上述 7 种模式进行排查
2. 对每个发现标注模式编号（如 `[Pattern-3: Missing Guard]`）
3. 在结论中说明哪些模式与当前异常直接相关，哪些为潜在风险
