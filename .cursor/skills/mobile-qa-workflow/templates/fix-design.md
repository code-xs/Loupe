# Fix Design Document 模板

```markdown
## Fix Design Document — {Issue-ID}

### 关联信息
- **Root Cause Report ID**: [关联]
- **根因置信度**: [0.XX] ([High/Medium/Low]) — 决定修复策略保守度

### 选定方案概述
- **修复策略**: [策略名称]
- **策略类型**: [治本 / 治标（须说明为什么不选治本）]
- **变更范围**: [文件列表 + 预估变更行数]
- **一句话描述**: [这个修复做什么，为什么这么做]

### 形式化论证

#### 论证 1: 根因覆盖性（Completeness）
- **因果链**: A → B → C → D(异常)
- **本修复切断环节**: B → C
- **论证**: [为什么切断 B→C 足以消除问题，C 不会从其他路径被触发]

#### 论证 2: 副作用安全性（Safety）
- **修改函数/方法**: [函数名]
- **调用者分析**:
  - caller1: [不受影响，因为...]
  - caller2: [不受影响，因为...]
  - caller3: [⚠️ 需关注，因为... → 已在修改中处理]
- **共享状态/资源分析**: [是否涉及共享状态，影响分析]
- **并发场景安全性**: [是否存在并发风险]
- **平台差异性影响**: [修改在另一平台是否有不同影响]

#### 论证 3: Spec 一致性（Correctness）
- Expected Behavior 1: [满足，因为修复后...]
- Expected Behavior 2: [满足，因为修复后...]
- Invariant 1: [维护，因为...]
- Invariant 2: [维护，因为...]
- **边界条件**: [覆盖 / 需额外处理]
- **异常路径**: [覆盖 / 需额外处理]

#### 论证 4: 最小性（Minimality）
- [论证当前方案是合理的最小变更]
- [是否存在更小范围的修改能达到同等效果？否，因为...]
- [是否包含非必要的"顺手"改动？否]

### 跨平台处理
- **Android**: [具体修改内容 + 平台特异性说明]
- **iOS**: [具体修改内容 + 平台特异性说明]
- **一致性评估（三层分级）**:
  - L1-视觉一致性: [两端 UI 呈现是否一致？允许的平台风格差异？]
  - L2-行为一致性: [功能逻辑和交互流程是否对齐？同一操作是否产生同一结果？]
  - L3-容错一致性: [异常处理、降级策略、错误提示是否对齐？]
- **差异说明**: [如有不一致，说明原因（平台限制/设计意图/技术约束）]

### 竞争方案记录（如有多方案评估）

#### 评估矩阵
| 评估维度 | 权重 | 方案A 评分 | 方案B 评分 | 方案C 评分 |
|---------|------|----------|----------|----------|
| 根因覆盖度 | 30% | | | |
| 副作用风险 | 25% | | | |
| 变更最小性 | 15% | | | |
| 跨平台一致性 | 10% | | | |
| 可回滚性 | 10% | | | |
| 长期可维护性 | 10% | | | |

评分 1-5 分；最终得分 = SUM(评分 × 权重)

- **方案B**: [简述] | 未选择原因: [...]
- **方案C**: [简述] | 未选择原因: [...]

### 回归测试设计
- [TC1] **直接验证**: [验证修复是否生效]
- [TC2] **边界验证**: [验证边界条件]
- [TC3] **回归验证**: [验证相关功能未被破坏]
- [TC4] **跨平台验证**: [验证双端一致性]

### 回滚方案
- **回滚方式**: [revert commit / feature flag / 配置下发]
- **回滚影响**: [回滚后的已知影响]
- **回滚触发条件**: [什么情况下应该回滚]
```
