# `mobile-qa-b2c-workflow-design.md` 架构与流程设计深度评审报告

## 1. 评审范围与方法

### 1.1 评审对象
- 文档：`mobile-qa-b2c-workflow-design.md`
- 范围：整体架构、Phase 1-6、Skill 实现约定、文件清单、方案落地可行性

### 1.2 评审方法
- **完整性审查**：检查是否覆盖“发现问题 -> 定义规范 -> 归因 -> 修复 -> 验证 -> 沉淀”全生命周期
- **一致性审查**：检查各阶段输入输出是否可闭环、术语是否一致、判定门槛是否统一
- **可执行性审查**：检查是否可被团队真实执行（角色、产物、度量、时效、工具依赖）
- **风险审查**：识别高风险断点、误判路径、实施阻塞点
- **量化评分**：给出维度化质量评分与优先级改进项

## 2. 总体结论（Executive Assessment）

### 2.1 结论摘要
- 该方案是一个 **结构完整、工程化意识较强** 的移动端 B2C 质量治理框架，核心优势在于：
  - 用 Spec 作为事实锚点，降低“凭经验拍脑袋”的归因偏差
  - 引入结构化推理链与多 Agent 对抗，提升复杂问题定位可靠性
  - 将修复从“写代码”提升到“论证正确性”，质量思路先进
- 同时，当前版本存在 **“方法论强、运营化细节不足”** 的落地风险：
  - 对角色分工、SLA、证据质量标准、自动化集成接口定义不够具体
  - 置信度公式和评分机制仍偏启发式，缺少标定与可复现实验基线
  - 多 Agent 深度路径成本高，缺少触发阈值与降级策略的量化门槛

### 2.2 整体质量评分（10 分制）
- **架构完整性**：9.0
- **流程闭环性**：8.8
- **可操作性**：7.4
- **可度量性**：7.0
- **落地可行性（组织+工具+成本）**：7.2
- **风险控制成熟度**：7.6
- **综合评分**：**7.8 / 10（可落地，但需补齐运营化与量化治理）**

### 2.3 发布建议
- 建议状态：**“可进入试点（Pilot）”**，不建议直接全量推广
- 建议路径：先在 1-2 条业务线灰度落地，完成指标标定后再扩展

## 3. 逐环节架构与流程深度 Review（不遗漏覆盖）

## 3.1 总体架构（设计理念 + Skill 体系 + 总流程）

### 优点
- “Spec 驱动 + AI 辅助 + B2C 导向”定位清晰，兼顾工程严谨性与用户上报场景现实性
- 六阶段主流程与回退路径完整，具备质量闭环特征（Phase2/4/6 可回流）
- Skill 分层结构清楚，具备可模块化实施基础

### 风险与缺口
- **角色治理缺口**：缺少 RACI（谁决策、谁执行、谁审批、谁知会）定义
- **流程入口治理缺口**：未定义多入口（客服、社区、应用商店、埋点告警）统一归一策略
- **状态机缺口**：主流程虽有图，但缺少工单状态字段规范（如 `Open/Spec-Uncertain/RCA-InProgress/Blocked/Verified/Closed`）

### 建议
- 增加“工作流状态字典 + 转移条件 + 责任人”
- 明确“人工接管点”（例如置信度低、跨端争议、证据冲突时必须人工裁决）

---

## 3.2 Phase 1：问题受理与分类（mobile-qa-intake）

### 优点
- 已定义标准分类树与 Issue Card，输入结构化基础扎实
- 关注 B2C 模糊描述场景，符合真实用户反馈特性

### 风险与缺口
- **分类一致性风险**：缺少分类冲突处理规则（如“功能+网络+兼容”复合问题）
- **优先级判定主观性**：P0-P3 未给量化标准（影响用户数、损失金额、舆情等级）
- **信息质量门槛缺失**：未定义“可分析最小信息集”（例如无复现路径时如何补采）

### 建议
- 增加“主分类 + 次分类 + 置信度”机制
- 定义优先级计算公式：`Severity x Reach x Detectability x BrandRisk`
- 设立 Intake 质量门禁：信息不全进入“补证据队列”而非直接推进

---

## 3.3 Phase 2：Spec 定义与上下文收集（mobile-qa-spec-definition）

### 优点
- Base Spec（Expected/Actual/Invariant）定义准确，是后续归因和验证高质量基础
- 分类扩展模块设计全面，覆盖功能/UI/网络/兼容典型证据需求
- 引入 Spec 校准和 “非 Bug” 逃逸路径，具备业务现实性

### 风险与缺口
- **Spec 版本治理缺失**：未定义 Spec 变更后的版本追踪与历史对比机制
- **证据可信度等级缺失**：日志、抓包、截图、用户口述权重未标准化
- **隐私合规风险**：上下文收集涉及日志与设备信息，未定义脱敏规范（PII/token/device id）
- **非 Bug 误杀风险**：缺少“复审机制”，可能把真实缺陷过早判为 WAD

### 建议
- 新增 `Spec Versioning`（v1/v2 + 变更原因 + 影响分析）
- 建立证据评级：A（可复现实证）/B（间接证据）/C（口述）
- 增加数据合规章：采集最小化、脱敏、留存周期、访问审计
- “非 Bug” 增加二次复核与抽检策略

---

## 3.4 Phase 3：根因分析（mobile-qa-root-cause，核心）

### 优点
- 复杂度分级、结构化推理链、边界判定、对抗分析、仲裁机制形成较完整推理体系
- 引入反事实验证和置信度评分，明显优于单点经验判断
- 平台专项检查清单具备实操价值（Android/iOS 关键盲区覆盖较好）

### 风险与缺口
- **成本与时效风险（高）**：多 Agent 对抗分析在人力与算力上成本高，缺少触发阈值
- **评分可重复性风险（高）**：置信度公式依赖主观权重，缺少校准数据集
- **证据依赖质量风险（中高）**：若 Context Bundle 质量低，多 Agent 只会“放大噪声”
- **边界争议升级风险（中）**：客户端-服务端归属判定未定义争议升级路径与仲裁时限

### 建议
- 设“深度路径触发器”：
  - 仅当 `P0/P1` 且 `快速路径失败` 或 `跨模块不确定性高` 才启用多 Agent
- 建“RCA 标定集”：用历史已闭环案例回放，持续标定评分权重
- 引入“最小证据阈值”：低于阈值禁止进入深度路径
- 明确跨端争议 SLA（如 24h 初判、48h 联合复判）

---

## 3.5 Phase 4：修复方案设计（mobile-qa-fix-design，核心）

### 优点
- 四重论证（覆盖性/安全性/一致性/最小性）非常关键，能显著降低“修好一个坏两个”
- 多方案评估矩阵与策略知识库可复用价值高
- 强调“治本优先、治标兜底”，方向正确

### 风险与缺口
- **评分矩阵主观偏置**：未定义评分人和评审机制（个人打分偏差大）
- **变更影响分析不足**：缺少与依赖图、调用链、实验平台联动要求
- **跨平台一致性判据不足**：未定义“允许差异”和“必须一致”的红线清单

### 建议
- 评估矩阵改为“双人打分 + 评审会仲裁 + 理由留痕”
- 引入自动化影响分析（调用链/模块依赖/AB 开关影响）
- 定义跨平台一致性分级：视觉一致、行为一致、容错一致三层标准

---

## 3.6 Phase 5：修复实施（mobile-qa-fix-impl）

### 优点
- 明确“单一职责、最小变更、防御性编程、双端一致性”
- 实施检查清单有基础可执行性

### 风险与缺口
- **工程门禁缺失**：未明确 CI 必须项（单测覆盖阈值、静态扫描、性能基线）
- **分支策略缺失**：未定义 hotfix/release 分支策略与 cherry-pick 规范
- **变更可追溯性不足**：缺少“实现 -> 设计论证 -> RCA”双向链接要求

### 建议
- 建立 CI Gate：测试通过率、覆盖率、Lint、关键性能阈值
- 增加 Git 流程规范：修复分支命名、回滚分支、发版节奏
- PR 模板强制关联 `Issue Card / RCA / Fix Design`

---

## 3.7 Phase 6：验证与闭环（mobile-qa-verification）

### 优点
- 三层验证模型（Spec 符合性/回归安全性/发布质量）逻辑正确
- Knowledge Card 有助于从“修复事件”沉淀到“预防资产”

### 风险与缺口
- **发布质量指标不具体**：性能“无劣化”缺少量化阈值（如启动时长、ANR率）
- **线上观测闭环不足**：未定义发布后观察窗、回滚阈值与告警策略
- **知识库运营缺口**：缺少标签标准、检索策略、失效知识淘汰机制

### 建议
- 定义可观测指标基线：Crash Free、P95 启动时长、关键链路成功率等
- 增加“发布后 24h/72h 观察策略 + 自动告警 + 回滚阈值”
- 制定知识库治理策略：标签词典、季度清洗、命中率统计

---

## 3.8 Skill 实现约定与文件清单

### 优点
- 文件组织清晰，主指令与参考文档分离合理
- 对 SKILL.md 行数上限有约束，利于可维护性

### 风险与缺口
- **模板规范缺失**：虽有模板清单，但未定义模板字段强制校验规则
- **编排器契约缺失**：各 Phase 输入输出 JSON Schema 未标准化
- **版本与兼容管理缺失**：Skill 升级后向后兼容策略未定义

### 建议
- 为每个模板定义必填字段、字段类型、校验规则
- 统一各 Phase 的 I/O Schema（可用于自动化编排与审计）
- 增加 Skill 版本号与兼容声明（`semver` + 迁移说明）

## 4. 方案落地可行性评估

## 4.1 组织可行性
- 当前方案需要至少四类角色协同：客服/QA/客户端研发/后端对口人
- 若没有专门“质量编排角色”，多阶段交接会导致推进变慢
- **评估**：中等可行（需要明确 owner 机制）

## 4.2 工具与数据可行性
- 依赖日志、抓包、历史变更、知识库检索、自动化测试链路
- 若现有平台未打通（工单系统、代码仓、监控平台），流程执行成本会明显增大
- **评估**：中等偏低（先打通基础集成后再扩面）

## 4.3 时效与成本可行性
- 简单问题可受益明显；复杂问题若全部走深度路径，成本高
- 建议按优先级和不确定性进行“分析资源分层投入”
- **评估**：中等（需强制分层策略）

## 4.4 质量收益可行性
- 方案对“误判、漏判、回归风险”有系统性抑制能力
- 若量化指标落地到位，中期可显著提升 MTTR 与一次修复成功率
- **评估**：较高（前提是指标治理到位）

## 4.5 综合可行性评级
- **当前可行性：B（可试点）**
- **达成 A 级条件**：
  - 建立量化 SLA 与门禁
  - 打通工具链与证据采集
  - 完成多 Agent 成本控制与触发规则

## 5. 关键风险清单（按优先级）

| 优先级 | 风险项 | 影响 | 建议措施 |
|---|---|---|---|
| P0 | 多 Agent 深度路径无触发门槛，分析成本失控 | 时效下降、团队疲劳、资源浪费 | 定义触发条件 + 降级策略 + 单次分析预算 |
| P0 | 置信度评分缺少标定数据，结论可重复性不足 | 决策可信度下降 | 建立历史案例标定集，季度校准权重 |
| P1 | 数据采集合规规则缺失 | 隐私与合规风险 | 增加脱敏、留存、访问审计规范 |
| P1 | 非 Bug 逃逸可能误判真实缺陷 | 用户体验受损、重复投诉 | 二次复核与抽检，保留回流通道 |
| P1 | 跨端边界争议缺少升级与时限机制 | 协作阻塞、责任不清 | 设定联合判定 SLA 和升级路径 |
| P2 | 知识库治理机制不足 | 复用率下降、经验失真 | 标签标准化、定期清洗、命中率考核 |

## 7. 改进路线图（落地执行建议）

## 7.1 0-30 天（试点准备）
- 输出 RACI、SLA、状态机、优先级与证据评级标准
- 为 Phase 1-6 制定统一 I/O Schema
- 打通最小工具链：工单系统 + 代码仓 + 日志平台

## 7.2 30-60 天（小范围试点）
- 选择 1-2 个核心业务模块试点
- 建立 `RCA 标定集`（至少 30 个历史案例）
- 启用分层触发策略（快速路径默认，深度路径受控）

## 7.3 60-90 天（评估与扩展）
- 复盘关键指标：MTTR、一次修复成功率、回归率、误判率
- 根据试点数据调整置信度权重与评估矩阵
- 扩展到更多业务线并完善知识库治理机制
