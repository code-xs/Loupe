# Intake Form（受理采集表）

下方字段为**统一信息模型**；支持两种受理方式，**二选一或组合使用**，最终都落到同一份 `issue-card.md`。

---

## 两种受理场景（系统自动判定）

| 模式 | 适用场景 | 用户行为 | Agent 行为 |
|------|----------|----------|------------|
| **A. 交互式（Interactive）** | 聊天里逐步说清楚、或不确定要提供什么 | 口头/分段描述；用户可不提前填表 | 以本表为清单，**在对话中分轮搜集**，边收边写入 Issue Card；**仅当「必填」仍缺时**再发起封闭式确认，不预先要求用户交长文档。 |
| **B. 文档式（Document）** | 已有现成说明、飞书/工单里写好了 | 提交**问题描述清单/文档**全文，或 **文档 URL**（飞书/语雀/Confluence/Wiki 等） | **解析**正文与结构，映射到 Issue Card；文档未覆盖的字段标 `[Context-Gap]`；**仅当「必填」仍缺时**再向用户确认。 |

**汇合规则（两种模式相同）**

1. 字段含义与「通用 / 按类型加严」矩阵以本文件为准；用户无需填写“受理模式”。  
2. **必选项**（见下表「必填」及按问题类型加严的「必填」）：缺失则 **Info-Insufficient**，用 **选择题 / 封闭式** 一次问清缺失项，补齐后再进入下一阶段。  
3. **选填 / 建议必填**：缺失可标 `[Context-Gap]` 并继续，或在交互式中下一轮顺带问一句；**不因选填缺失而阻塞**，除非流程另有要求。  
4. 来源标注：用户直接给出的标 `[User-Provided]`；Agent 归纳标 `[AI-Inferred]`（C 级）；APM 拉取单独列出。

---

## 模式 A：交互式 — 建议对话节奏（Agent 参考）

1. 首轮识别平台 + 问题类型 + 一句话现象 + 预期效果。  
2. 次轮补齐「通用」中的必填：可复现性、基础环境（版本/机型/OS 能拿多少拿多少）。  
3. 按主分类追问该类型的**必填**证据（如 Crash 要堆栈摘要）。  
4. 对照矩阵补「建议必填」；缺则记入缺失项，不强行打断。  
5. 输出 Issue Card 前再跑一遍**必填门禁**，仍缺则只问缺的那几项。

---

## 模式 B：文档式 — 提交物格式

- **粘贴全文**，或上传 `.md` / `.txt` / 飞书导出。  
- **文档 URL**：需可读；无权限时请用户**导出全文粘贴**。  
- Agent 解析后同样执行 **必填门禁**，缺失项用封闭式问题确认。

> 自动判定规则：若用户提供了问题描述清单/成篇文档（含 URL），默认按 **document** 处理；否则按 **interactive** 处理。

**图例**：`必填` = 进入 RCA 前必须补齐；`选填` = 有则填，无则标 `N/A` 并说明原因。

## 0. 通用（所有类型）

| 字段 | 必填性 | 说明 |
|------|--------|------|
| 问题类型 | 选填（强参考） | 可由用户填写；AI会自动分类。若用户已填，作为主要参考，但仍需与证据校验一致性。 |
| 平台 | 必填 | Android / iOS / Both |
| 问题描述 | 必填 | 实际发生了什么（Actual Behavior） |
| 预期效果（Expected Behavior） | 必填 | 你希望系统应如何表现（修复目标基线） |
| 可复现性 | 必填 | 必现 / 偶现 / 仅一次 |
| **仓库路径** | 选填 | 本地或远端仓库根路径/URL；纯线上反馈无代码可填 `N/A` |
| **仓库分支** | 选填 | 当前排查或发布对应分支名；无分支信息填 `N/A` |
| **代码 diff / patch** | 选填 | 已本地修改时：**必填**贴 `git diff` 或 `.patch` 文件路径/附件；无改动填 `无` |
| **需求文档（PRD）** | 选填 | 链接或文档 ID；功能/交互类问题见下表加严 |
| **技术方案** | 选填 | 设计文档/ RFC / 技术评审结论链接；涉及架构或协议时见下表加严 |

## 1. 按问题类型的加严规则（在「通用」基础上叠加）

| 字段 | 稳定性<br>Crash/ANR/OOM | 功能 | UI/UX | 网络 | 兼容性 | 性能 | 安全 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| 仓库路径 | 选填→**建议必填**（需定位代码时） | 选填→**建议必填** | 选填→**建议必填** | 选填→**建议必填** | 选填→**建议必填** | 选填→**建议必填** | 选填→**建议必填** |
| 仓库分支 | 选填 | 选填 | 选填 | 选填 | 选填 | 选填 | 选填 |
| 代码 diff / patch | 选填（**已改代码则必填**） | 同左 | 同左 | 同左 | 同左 | 同左 | 同左 |
| 需求文档 | 选填 | **必填**（无则说明「无书面 PRD」） | **必填**（涉及视觉/交互契约时） | 选填 | 选填 | 选填 | 选填 |
| 技术方案 | 选填 | 选填→**建议必填**（业务规则复杂时） | 选填 | **建议必填**（协议/网关/重试策略） | **建议必填**（SDK/系统 API 选型） | 选填→**建议必填**（指标口径） | **必填** |

> **说明**：「建议必填」= 门禁上仍允许 `[Context-Gap]` 进入下一阶段，但必须在 Issue Card 的「缺失项」中列出并追齐。
>
> **问题类型判定规则**：若用户填写了问题类型，先作为主参考；AI需结合日志、堆栈、复现路径与上下文做一致性校验。若不一致或置信度低，使用封闭式问题向用户确认后再定类。

## 2. 字段格式约定

- **仓库路径**：示例 `https://code.byted.org/org/repo` 或 `/Users/me/work/app`
- **仓库分支**：示例 `release/8.3.1`、`feature/foo`
- **代码 diff / patch**：优先附件或代码块；大 diff 可写 `见 qa-workspace/{issue_id}/changes.patch`
- **需求文档**：`[标题](URL)` 或 `飞书 doc_token：xxx`
- **技术方案**：同上；若无独立文档，可写「见某 PR 描述 / 评审记录链接」

---

## 3. 与 Issue Card 的映射

| Intake Form | Issue Card 章节 |
|-------------|------------------|
| 本表全文 | 可附在 `issue-card.md` 末尾「附录：Intake 原始表」，或工作区内单独 `intake-submission.md`；**文档 URL** 写入「信息来源」 |
| 仓库/分支/diff/PRD/技术方案 | **代码与文档上下文** |

## 4. 自检清单

**文档式用户**提交前可打勾：

- [ ] 「通用」里所有 **必填** 项已填或已写 `N/A` 原因（问题类型可不填）  
- [ ] 已对照「按问题类型」矩阵补齐 **必填**（及力所能及的 **建议必填**）  
- [ ] 稳定性类已附堆栈/日志等客观证据或等价材料  
- [ ] 若提供 URL：链接可读，或已改附全文  

**交互式**可由 Agent 在产出 Issue Card 前代为对照本清单（仅硬拦 **必填**）。
