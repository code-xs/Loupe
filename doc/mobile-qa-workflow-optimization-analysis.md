# Mobile QA 工作流优化：海量相似代码与模糊问题边界的应对方案

## 1. 背景与挑战

当前 Mobile QA 工作流基于 **OVHSC（观察-假设-验证-打分-因果链）** 推理链和多 Agent 对抗机制，在逻辑推演层面提供了强大的约束。然而，在面对实际的大型移动端工程时，AI 在“上下文获取”环节面临着严峻挑战，主要体现在以下两个维度的交叉干扰：

### 1.1 海量相似代码带来的“幻觉锚定”
*   **A/B 实验遗留**：代码库中往往同时存在 `FeatureV1` 和 `FeatureV2`，甚至更多的实验分支代码。
*   **跨端/跨业务线复用**：不同业务线可能 copy 了相似的基类或组件，命名高度一致。
*   **废弃死代码**：历史下线的业务代码未及时清理。
*   **影响**：当 AI 依赖纯静态的“语义搜索”或“关键字 Grep”时，极易抓取到未执行的相似代码（如死代码或未命中的 AB 分支），并对着错误的上下文进行完美的逻辑推演，导致“幻觉锚定”。

### 1.2 问题引入边界（Issue Introduction Boundary）的不确定性
问题的描述往往具备不同的边界清晰度，这直接决定了搜索空间的大小：
*   **高清晰度（精确到 MR/需求）**：知道是某次提交引起的，但变更可能散落在多个重构文件中。
*   **中清晰度（精确到集成版本）**：只知道是 v1.2 升级到 v1.3 引入的，期间包含了数百个 MR，搜索空间呈指数爆炸。
*   **低清晰度（历史遗留/偶现问题）**：跨越了多次架构演进，存在多套平行代码，静态搜索的误导性极强。

---

## 2. 核心优化思路：引入“问题边界感知”与“上下文策展”

为了解决上述问题，工作流不能再采用“一刀切”的全局静态搜索，必须向**“动态过滤、精准切片”**演进。核心策略包括：

1.  **增加“Context Curator (上下文策展人)” 角色**：专职负责对搜索到的代码进行“存活性”和“相关性”审查，剔除死代码和干扰项。
2.  **依据“问题边界”动态切换检索策略**：根据问题是定位到 MR、版本还是历史遗留，采用完全不同的切入点。
3.  **强化动态运行数据的“硬约束”**：将 APM、堆栈、日志作为最高优先级的锚点，强制静态代码必须能与动态痕迹映射。

## 3. 具体改进方案（按问题边界分类）

### 3.1 场景一：边界清晰（精确到某个需求或 MR）

**特征**：明确知道是由哪次代码合并引起的。
**挑战**：重构导致的大量相似代码变更，难以快速定位关键逻辑点。

**工作流优化动作**：
1.  **强制 Diff 驱动分析 (Diff-Driven Analysis)**
    *   在 `Phase 2 (Spec 定义)` 阶段，若识别出关联 MR，工作流必须强制拉取该 MR 的 Diff 文件。
    *   在 `Phase 3 (根因分析)` 中，将 Diff 覆盖的代码片段标记为**最高优先级（A级证据）**。
    *   **约束**：若生成的假设完全未涉及 Diff 中的变更，其置信度得分应被强制削减（如乘以 0.5 的惩罚系数）。
2.  **Grep 与 Git Blame 联合校验**
    *   在搜索相似代码时，强制结合 `git blame`，优先关注属于该 MR 提交者和时间范围的代码行。

### 3.2 场景二：边界模糊（只能定位到某个集成版本）

**特征**：知道是版本迭代（如 v1.2 -> v1.3）引入的，但期间包含了成百上千个 Commit。
**挑战**：搜索空间巨大，无法直接看代码。

**工作流优化动作**：
1.  **提交日志降噪 (Commit Log Denoising)**
    *   在进入代码推演前，插入一个“版本变更筛查”步骤。
    *   提取版本间的 `git log`，结合问题分类（如“网络”、“UI”）和报错模块路径，过滤出高相关性的 Commit 集合（从数百个降维到十几个）。
2.  **二分法辅助提示 (Bisection Prompting)**
    *   如果环境支持 Git 且本地可编译，工作流可在 `Phase 3` 抛出 `step-pause`，建议用户配合执行 `git bisect` 以快速缩小范围，或者请求用户提供“上一个正常版本”和“当前异常版本”的具体 Commit Hash。

### 3.3 场景三：边界极其宽泛（历史遗留问题、宽泛描述）

**特征**：问题存在已久，可能跨越多代架构，充斥着大量 A/B 实验或废弃的相似代码。
**挑战**：全局静态搜索极易命中“死代码”或未激活的分支。

**工作流优化动作**：
1.  **强制动态数据锚定 (Dynamic Data Anchoring)**
    *   对于历史问题，**禁止** AI 直接进行全局关键字搜索。
    *   在 `Phase 1 (Intake)`，若缺乏动态运行日志（Crash 堆栈、Method Trace、抓包等），触发强制停顿（`Info-Insufficient`），要求用户补充。
2.  **自底向上的逆向推演 (Bottom-Up Tracing)**
    *   **约束**：强制 AI 从“案发现场”（如崩溃栈顶、网络请求拼装报错处）开始，利用“查找所有引用 (Find Usages)”或“调用层级 (Call Hierarchy)”向上回溯。
    *   **优势**：通过真实的调用链向上找，自动避开了那些同名但未被引用的废弃类。
3.  **配置快照掩码 (Config Snapshot Masking)**
    *   强制获取用户/设备的 Feature Flag 和 AB 实验命中状态。
    *   在代码分析时，将这些开关状态作为“掩码”。如果检索到的某段相似代码入口开关为 `false`，则直接将其从上下文中剔除。

## 4. 架构级改进建议（工作流元数据扩展）

为了支撑上述动态策略，工作流的状态机（如 `workflow.xml` 和 `workflow-status.yaml`）需要引入新的元数据：

1.  **增加 `Issue_Boundary_Level` 字段**
    *   在 Intake 阶段评估，取值为：`EXACT_MR` | `VERSION_RANGE` | `HISTORICAL_UNCLEAR`。
    *   `Phase 3` 的路径选择（Switch/Case）将不再仅仅依赖问题复杂度，而是结合该字段决定是走“Diff 聚焦模式”、“Commit 过滤模式”还是“动态逆向溯源模式”。
2.  **引入 `Context_Curator` 子 Agent**
    *   在拉起 Investigator 之前，先运行 Curator Agent。
    *   Curator 的职责是：拿到初步检索的代码 -> 运行 `git blame` 查年份 -> 运行静态引用查找看是否是死代码 -> 核对 AB 实验开关 -> 输出“净化后”的 Context Bundle。
3.  **强化 Challenger 的时空维实质询**
    *   扩展 Challenger 的五维质疑协议，增加“时空维度”：如果老代码突然出问题，强制要求 Challenger 质疑其依赖的底层 API、远端配置或数据契约是否近期发生了变更，而非死磕老代码本身的逻辑。

## 5. 总结

面对海量工程和模糊边界，AI 辅助 QA 不能仅做“逻辑推演器”，更要做“优秀的档案管理员”。通过将**“问题边界感知”**作为核心路由条件，并结合**动态数据硬锚定**与**自底向上溯源**，可以有效收束 LLM 的搜索空间，大幅降低相似代码带来的幻觉干扰，使工作流的归因分析更加精准和工程化。
