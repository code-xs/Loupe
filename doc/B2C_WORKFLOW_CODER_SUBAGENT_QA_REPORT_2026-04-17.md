## 1. 执行摘要

本次质检覆盖了当前仓库中 B2C 质量问题工作流的主入口、核心编排 DSL、六阶段实现、核心规则、模板、专项子工作流以及评测门禁链路，并对飞书方案《Coder SubAgent 技术方案 V1》进行了逐项对照分析。

综合结论如下：

1. **当前 B2C 工作流主骨架成熟，流程设计完整度较高。**
   现有实现已具备：
   - 基于 `SKILL.md -> core/workflow.xml -> phases/p1~p6` 的稳定编排结构
   - 明确的状态机与 `step-pause` 人工确认机制
   - `invoke-subagent` 标签语义、黑盒透传规则与人审协议
   - `functionality-deep-dive` 专项子工作流与主链路的联动机制
   - `defensive-fix-design.md` 从专项工作流回注到 P5 修复实施阶段的消费通道

2. **当前实现仍停留在“主 Agent 直接执行修复实施”的模式，尚未落地飞书方案中最核心的 Coder SubAgent 黑盒改造。**
   飞书方案的核心价值点是：
   - 将 P5 修复实施彻底下沉到独立 `coder-agent`
   - 强制执行“契约溯源 -> 精确编码 -> 微验证纠错 -> 报告移交”的四阶段闭环
   - 在编码前建立强约束的“查定义、查资源、查契约”机制，抑制低级幻觉
   但这些关键能力在现状中**尚未形成可运行闭环**。

3. **从质量视角看，该方案方向正确、问题抓得准、收益明确，但当前仓库仅具备“接入基础”，并未完成实际落地。**
   简单说：
   - 方案质量：**高**
   - 实现现状：**部分具备承接条件，但尚未接入**
   - 当前验收结论：**未达到“方案已落地可验收”状态**

4. **若不补齐 Coder SubAgent、Contract Checklist、I/O 契约、模板扩展与评分改造，方案将停留在设计层，无法真正提升一次修复通过率。**

本报告最终建议的结论为：

- 对当前 B2C 主工作流：**通过基础架构质检，但 P5 质量闭环仍存在关键缺口**
- 对 Coder SubAgent 方案：**建议采纳，但应视为“待落地方案”，当前不可宣称已实现**
- 对验收状态：**不建议直接通过；应先完成 P5 架构级接入改造后再进行二次质检**

## 3. 当前 B2C 工作流实现全景分析

## 3.1 总体架构

当前 B2C 工作流采用典型的“入口 Skill + XML DSL 编排 + 分阶段执行 + 模板产物 + 状态文件路由”的体系。

主链路如下：

1. `SKILL.md` 作为 Full 平台入口
2. 初始化或恢复问题工作区
3. 检测文件系统 / Git / Lint / 子 Agent 能力
4. 加载 `core/workflow.xml`
5. 基于 `workflow-status.yaml` 判定当前阶段
6. 依次执行六阶段：
   - `qa-intake`
   - `qa-spec-definition`
   - `qa-root-cause`
   - `qa-fix-design`
   - `qa-fix-impl`
   - `qa-verification`

该分层设计清晰、职责边界明确，是当前实现的显著优点。

## 3.2 入口层实现质量

`mobile-qa-workflow/SKILL.md` 已完成以下关键职责：

- 定义工作流输入参数
- 管理问题工作区路径
- 新问题与已有问题恢复逻辑
- 初始化默认配置文件与状态文件
- 检测环境能力
- 将上下文转交给核心编排器 `core/workflow.xml`

这说明当前实现已经具备“流程级编排框架”的稳定入口，不是一个松散的 Prompt 集合，而是一套可恢复、可路由、可持久化的工作流框架。

从工程化成熟度看，这一层的设计是合格的。

## 3.3 编排器质量

`mobile-qa-workflow/core/workflow.xml` 的质量整体较高，主要体现在：

### 优点

1. **Phase I/O 契约显式化**
   每个阶段的输入输出都在 `<io-contract>` 中声明，利于审计、恢复和后续扩展。

2. **状态路由完整**
   `Info-Insufficient`、`Spec-Uncertain`、`Non-Bug`、`RCA-LowConfidence`、`Human-Review`、`Boundary-Refined`、`Curation-Failed`、`Closed` 等路径都有编排层承接。

3. **状态持久化意识强**
   阶段完成后会更新：
   - `stepsCompleted`
   - `lastStep`
   - `current_state`

4. **支持流程恢复**
   通过 `workflow-status.yaml` 可以恢复中断进度，而不是依赖模型记忆。

### 局限

编排器在 Phase 5 的 I/O 契约仍旧停留在旧模型：

- 输入：`fix-design.md, spec.md`
- 输出：`impl-report.md`

这意味着编排器层**尚未承认**飞书方案新增的 `contract-checklist.md` 为正式产物，因此即使后续补齐 Phase 5 逻辑，编排器也还不具备对新产物的显式协作能力。

这将直接影响：

- Phase 5 的产物完整性定义
- Phase 6 对溯源记录的消费能力
- 评测系统对“契约溯源”能力的审计能力

因此，编排器层对新方案的承接目前是不完整的。

## 4. 分阶段实现审计

## 4.1 Phase 1：问题受理（qa-intake）

当前 P1 实现较成熟，体现出较强的 B2C 质量问题流程意识：

- 支持 `document` / `interactive` 双模式汇流
- 有明确的最小信息集门禁
- 有边界等级与动态锚点盘点机制

从质量视角看，P1 已经不是简单问答，而是在为后续 RCA 做“分析前提清洗”。这一点是优点。

### 质检结论

- 设计合理：**是**
- 对后续 RCA 有实质价值：**是**
- 与飞书方案直接相关性：**中等**

P1 不是此次方案改造的重点，不构成主要风险点。

## 4.2 Phase 2：Spec 定义（qa-spec-definition）

P2 已经具备以下较强的工程化特征：

- 明确 Expected / Actual / Invariant 三元规约
- 按问题分类加载差异化扩展字段
- 有 Spec 冲突确认机制
- 有 Non-Bug 分流与回流机制
- 有候选上下文搜集与 Curator 策展机制
- 有 Reliability × Liveness 二维证据分级

这一阶段说明当前工作流不是“拿到问题就直接写代码”，而是在建立行为基准和证据质量控制。

### 质检亮点

1. 把“Spec 不清”视为真实流程状态，而不是隐式忽略
2. 上下文策展有独立子 Agent 概念，已具备多 Agent 协作思路
3. 能区分证据等级与存活性，明显优于普通缺陷排查 Prompt

### 质检风险

P2 已使用 `<invoke-subagent subagent_type="search">` 与 `curator`，说明系统已经接受“某些工作下沉到子 Agent”的思路。  
这会反向证明：**P5 不引入独立 Coder Agent，并不是框架做不到，而是当前尚未实现。**

- 专项结论回注主 RCA

### 质检评价

P3 的设计复杂度和成熟度很高，说明当前团队对“分析阶段”已经投入大量方法论建设。

这也带来一个重要观察：

这正是飞书方案要解决的核心矛盾：  
前面推得很细，后面写代码时仍可能靠概率猜测和经验主义补完。

## 4.4 Phase 4：修复方案设计（qa-fix-design）

P4 已经形成较完整的修复设计体系：

- 治本优先
- 远端漂移优先走协调修复
- 支持多 Agent 方案竞争与仲裁
- 有四重论证：
  - Completeness
  - Safety
  - Correctness
  - Minimality
- 有回归测试设计
- 有进入 P5 前的显式确认

### 质检评价

P4 的质量显著高于很多普通工程系统的“修复设计”阶段。  
但它的一个明显短板是：

> 当前 P4 产出的高质量 Fix Design，在 P5 中没有被“强约束地转化为安全代码实现”。

也就是说，P4 很强，但 P5 目前还不够强，造成前后链路质量断层。

## 4.5 Phase 5：修复实施（qa-fix-impl）

P5 是本次质检的**核心关注点**。

当前 P5 已经具备以下能力：

- 读取 `fix-design.md` 和 `spec.md`
- 读取平台检查清单
- 在专项 Deep-Dive 完成后加载 `defensive-fix-design.md`
- 区分代码修复与远端漂移/跨端协调修复
- 有 3 轮静态微验证重试机制
- 有 Human-Review 兜底
- 输出 `impl-report.md`

### 当前 P5 的优点

1. 已经意识到“防御性修复设计”必须贯穿到实施阶段  
2. 已经有微验证重试闭环，不是一次性拍脑袋改完就算
3. 有清晰的非代码修复分支，说明对“远端漂移不是客户端乱改代码”的原则有认知

### 当前 P5 的核心缺陷

尽管 P5 有这些优点，但从方案落地与质量控制视角，当前 P5 仍存在**架构级不足**：

#### 缺陷 1：仍由主 Agent 直接承担编码实施

这是最关键的问题。

现状中，P5 只是阶段文件中的一段流程 DSL，并没有把“实施”真正下沉到独立的 `coder-agent`。  
这意味着：

- 代码编写上下文与主工作流主上下文仍然耦合
- 编译报错、Lint 噪音会污染主 Agent 记忆
- 高层推理与底层纠错没有物理隔离
- 主 Agent 仍可能在高负载状态下产生低级幻觉

#### 缺陷 2：缺少编码前的契约溯源硬门禁

当前 P5 会读取平台检查清单，但没有要求在编码前先输出一个结构化 `contract-checklist.md`。  
因此：

- “是否真的去查了 API 定义”无法审计
- “是否真的核对了 XML 枚举值/资源 ID/配置键”无法审计
- “是否只是口头说做了防幻觉检查”无法审计

这类问题在移动端修复里极其关键，特别是：

- Android `attrs.xml` / `strings.xml` / `R` 资源名
- iOS `Info.plist` / `Localizable.strings` / `xcassets`
- 序列化字段名
- 路由键
- 平台 API 可用性

一旦没有“编码前查定义”的强制门禁，P5 仍旧容易退化为经验主义实施。

#### 缺陷 3：微验证闭环有重试，但缺少“每轮留痕”

当前 P5 有 `try retry="3"` 机制，但没有要求：

- 第 1 轮失败的错误摘要
- 错误对应文件/行号
- 重新溯源结果
- 修正动作
- 第 2 轮复验结果

这些关键过程没有结构化落入最终报告模板，导致：

- 失败现场难以复盘
- 无法判断自愈是否真实有效
- 无法量化“微验证自愈成功率”

#### 缺陷 4：工具约束缺失，无法强制“优先局部修改”

飞书方案提出“新增文件外优先 SearchReplace，避免覆写整文件”，这是非常正确的约束。  
但现状 P5 没有真正把这类规则变成流程强制项，因此不能从机制上限制粗暴改写行为。

### P5 质检结论

当前 P5 是“有质量意识的实施流程”，但还不是“强约束的安全实施闭环”。  
在工程成熟度上，属于：

- 比普通 AI 修复流程强
- 但距离飞书方案目标仍有明显差距

## 4.6 Phase 6：验证与闭环（qa-verification）

P6 设计整体合理：

- L1 Spec 静态符合性验证
- L2 静态影响面与回归安全性验证
- L3 发布质量验证
- 动态指标标记为 Pending-CI
- 失败时可回退到 Fix-Designing

- `spec.md`
- `fix-design.md`
- `impl-report.md`

如果未来引入 `contract-checklist.md`，Phase 6 本应消费其中的“定义溯源记录”，以验证：

- 修改是否真的建立在真实契约上
- 是否存在未核对资源键/字段名的风险

但当前 P6 对这一类证据无正式输入口。

这意味着：

> 即便未来 P5 生成了 Contract Checklist，P6 也还不能对它形成完整消费闭环。

## 7. 飞书方案《Coder SubAgent 技术方案 V1》专项质检

## 7.1 方案定位判断

该方案针对的问题定位非常准确，命中了移动端 AI 修复最常见的失败模式：

1. 上下文长链路后主 Agent 出现记忆疲劳
2. 编码时凭经验猜测资源、字段、枚举或方法签名
3. 一旦编译失败，大量报错噪音污染主上下文
4. 高质量 Fix Design 无法稳定转化为一次通过的代码实现

这四点都是真实的工程问题，而不是概念堆砌。  
因此，方案的立项方向是正确的。

## 7.2 方案核心设计评价

方案提出 Coder Agent 的四阶段实施闭环：

1. 契约溯源与防幻觉走查
2. 精确编码实施
3. 微验证与自我纠错沙盒
4. 产出与移交

从移动端质量工程视角看，这四段式结构是合理的，尤其是第一段“编码前契约溯源”非常关键。

### 方案优点

#### 优点 1：把“查定义”从建议升级为硬门禁

这会显著降低以下幻觉问题：

- 猜错 Android 自定义属性值
- 猜错资源键名
- 猜错序列化字段名
- 猜错 API 签名
- 猜错 iOS Plist 键

这类错误往往很低级，但极其常见。  
方案抓住了真正影响一次修复通过率的要害。

#### 优点 2：把“编译报错噪音”隔离到子 Agent 内部

这是方案非常专业的一点。  
很多 AI 工作流设计者会把注意力放在“让主 Agent 更聪明”，但这个方案更强调：

> 让主 Agent 不要被低价值噪音拖垮。

对移动端复杂工程场景来说，这是更有效的设计思路。

#### 优点 3：产物设计有审计价值

方案中的：

- `impl-report.md`
- `contract-checklist.md`

如果真正落地，将极大增强：

- 审计性
- 复盘能力
- 问题定位可追溯性
- 验证阶段可核查性

#### 优点 4：兼容 Full / Limited / Minimal 平台

方案没有把能力建立在单一平台特性上，而是给了降级路径，这一点较成熟。

## 7.3 方案中的主要风险

尽管方案方向很好，但也存在一些落地风险，需要在实施前明确。

### 风险 1：Contract Checklist 容易流于形式

如果不明确“哪些内容必须溯源”，模型可能会输出一个看似漂亮、实则空泛的 checklist。  
例如：

- 只写“已检查 API 正确”
- 不写定义文件
- 不写期望值
- 不写实际值

这会导致 Checklist 失去验收价值。

### 风险 2：SearchReplace 约束在不同平台可执行性不同

在 Full 平台可以作为强约束，但在 Limited 平台更多只能作为行为规范。  
因此需要区分：

- “平台能力可硬 enforce 的规则”
- “平台能力不足时只能审计的规则”

### 风险 3：微验证三轮上限虽合理，但需要结构化 Error Dump

方案提出 3 轮上限是对的，但若失败后没有标准化错误现场，Human-Review 也难高效接手。

### 风险 4：评测体系不改造，方案收益难量化

如果评分系统仍按旧维度评分，就无法证明：

- 契约溯源准确性提高了多少
- 幻觉错误减少了多少
- 自愈成功率提高了多少

这会导致方案改造后“体感变好了，但数据证明不了”。

## 8. 方案与现状对照审计

本节给出最关键的“方案 vs 现状”结论。

## 8.1 已具备的承接条件

当前仓库已具备以下承接基础：

1. `invoke-subagent` 机制已经存在
2. 主工作流已经大量使用子 Agent
3. 专项工作流和主流程之间已有回注链路
4. Human-Review 协议已定义
5. P5 已有“微验证重试”骨架
6. `platform-checklist` 已存在，可扩展通用溯源规则
7. `system-prompt.md` 已有 Limited 平台降级体系

因此，**引入 Coder Agent 在架构上是顺滑的，不需要推翻重做主框架。**

## 8.2 尚未落地的关键点

以下内容目前仍未在仓库中落地：

### 1. 未新增 `agents/coder-agent.md`

仓库内不存在：

- `mobile-qa-workflow/agents/coder-agent.md`
- 任何 `*coder-agent*` 命名文件

这意味着方案中的核心角色定义文件尚未进入代码库。

### 2. `core-rules.xml` 未注册 `coder-agent`

当前 `<available-agents>` 中没有 `coder-agent`。  
因此即使 Phase 5 想调用，也没有正式注册入口。

### 3. `p5-fix-impl.md` 未切换为黑盒 SubAgent 调用

当前 Phase 5 仍然由主 Agent 在流程内直接承担实施任务，未出现：

- `<invoke-subagent subagent_type="coder-agent" ...>`

这是当前方案未落地的最核心证据。

### 4. `workflow.xml` I/O 契约未扩展

当前 `qa-fix-impl` 的输出仍仅有：

- `impl-report.md`

没有：

- `contract-checklist.md`

### 5. `impl-report.md` 模板未扩展溯源记录与微验证纠错记录

当前模板只包含：

- 变更清单
- 静态微验证结果
- 检查清单
- 测试结果
- 风险

但没有结构化的：

- 契约溯源记录
- 每轮错误与修正记录
- defensive fix 留痕矩阵

### 6. `platform-checklist.md` 尚未增加“通用跨层契约溯源规则”

当前文件主要是 Android / iOS 检查清单，以及 API 版本合规。  
但还缺：

- 严禁臆测机制映射
- 强制定义溯源
- 溯源记录留痕

### 7. `system-prompt.md` 尚未把 Coder Agent 降级逻辑内联到 Phase 5

当前 Limited 平台的 P5 仍是旧版修复实施逻辑，没有内联契约溯源门禁。

### 8. 评分体系未适配

当前 `scoring-rubric-base.yaml` 中没有：

- 契约溯源准确性
- 幻觉识别率
- 自愈成功率

因此方案的关键收益无法在评测侧被量化。

## 9.1 P0 阻断项

## 10. 当前实现的优点总结

虽然本次报告指出了方案未落地的关键问题，但当前 B2C 工作流仍有很多值得肯定的设计质量，不应忽视。

### 优点 1：六阶段工作流逻辑闭环完整

从 Intake 到 Verification 都有文件化产物与状态流转，这比普通对话式 AI 方案成熟得多。

### 优点 2：分析阶段方法论成熟

P2、P3、P4 的设计明显经过深度打磨，尤其在证据质量、推理链和对抗式收敛方面具备很强专业性。

### 优点 3：专项子工作流设计优秀

`functionality-deep-dive` 不是装饰性模块，而是能对主链路 RCA 和修复实施产生真实影响。

### 优点 4：规则层具备强约束基础

`core-rules.xml` 说明系统已经从“Prompt 风格”走向“流程规则系统”，这一点对后续承接 Coder Agent 非常有利。

### 优点 5：已经具备部分“实施质量意识”

虽然 P5 还没做到方案要求的强度，但：

- 防御性修复
- 微验证
- Human-Review
- 非代码修复分支

这些基础意识已经存在，不是从零开始。

## 11. 专业质检结论

## 11.1 对当前 B2C 工作流的质检结论

结论：**主架构通过，P5 实施质量闭环不通过。**

解释如下：

- 若以“是否具备完整 B2C 质量工作流框架”评估：**通过**
- 若以“是否具备强约束、可审计、低幻觉的修复实施闭环”评估：**不通过**

也就是说，当前系统适合作为高质量工作流框架继续演进，但不能把当前 P5 能力等同于飞书方案中的 Coder SubAgent 实现。

## 11.2 对飞书方案的质检结论

结论：**方案方向正确，设计专业，建议采纳。**

原因：

- 目标问题真实
- 方案闭环完整
- 与当前框架兼容
- 能显著补齐 P5 质量短板

但同时必须强调：

> 方案现在是“高质量设计”，不是“已落地实现”。

## 11.3 对当前验收状态的结论

结论：**不建议直接验收通过。**

建议验收结论口径如下：

### 推荐结论文案

“当前 B2C 工作流主链路设计成熟，已具备承接 Coder SubAgent 方案的基础架构能力，但飞书方案中的核心改造点尚未实际接入。尤其是 `coder-agent` 注册、P5 黑盒实施、`contract-checklist.md` 产物链路、模板扩展与评测适配仍缺失。因此，本次评审建议将该方案判定为‘方向通过、实现待落地’，暂不建议以‘已完成改造’状态验收。”
